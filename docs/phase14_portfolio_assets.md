## 6. STAR Interview Answers

### STAR Answer 1: "Tell me about a challenging project"

**Situation:** I wanted to build a project that demonstrated production-level data science skills — not just model training, but the complete lifecycle from business understanding to deployment.

**Task:** Build an end-to-end Customer Churn Prediction Platform for a fictional telecom company, including ML pipeline, explainability, retention recommendations, and an executive dashboard.

**Action:** I structured the project into 15 phases. First, I wrote a Business Requirements Document with revenue impact calculations (₹31.2 Cr annual loss). Then I built a data pipeline: synthetic dataset generation, cleaning with quality reports, and 12 engineered business features. I trained 5 ML models with cross-validation and hyperparameter tuning. I implemented SHAP explainability to make predictions interpretable. I built a rule-based Retention Intelligence Engine that generates personalized recommendations. Finally, I created a 7-page Streamlit dashboard and containerized everything with Docker + GitHub Actions CI/CD.

**Result:** The best model (XGBoost) achieved 87% ROC-AUC. The SHAP analysis revealed actionable business insights — month-to-month contracts are the #1 churn driver. The retention engine identified that a 10% churn reduction could save ₹3.54 Cr annually. The entire pipeline runs in under 2 minutes and is deployment-ready.

---

### STAR Answer 2: "How do you handle imbalanced datasets?"

**Situation:** In the ConnectTel churn dataset, only ~26% of customers churned, creating a class imbalance that could bias the model toward predicting "no churn" for everyone.

**Task:** Ensure the model performs well on both classes, especially the minority (churn) class, without sacrificing overall accuracy.

**Action:** I used multiple strategies: (1) Stratified train-test split to maintain class proportions, (2) Stratified K-Fold cross-validation (5 folds) for robust evaluation, (3) Used class_weight='balanced' in models that support it, (4) Evaluated using Precision, Recall, F1, and ROC-AUC instead of just accuracy, (5) Focused on the Precision-Recall curve which is more informative than ROC for imbalanced data.

**Result:** The XGBoost model achieved 87% AUC with strong precision-recall balance. The F1 score was optimized to catch 75%+ of actual churners while maintaining 80%+ precision — meaning when we flag a customer, we're right 80% of the time.

### STAR Answer 3: "Explain a time you had to communicate technical results to non-technical stakeholders"

**Situation:** The churn prediction model outputs probabilities and SHAP values — highly technical outputs. But the CEO, marketing team, and customer success team need to act on these predictions.

**Task:** Translate complex ML outputs into actionable business language that non-technical stakeholders can use immediately.

**Action:** I built three layers of communication: (1) An Executive Insights Report that explains each churn driver in plain language — e.g., "Month-to-month contract customers are 3-5x more likely to churn" instead of "Contract_Month-to-month SHAP value = 0.35". (2) A Retention Engine that converts risk scores into specific actions: "Offer 15% discount on annual contract" instead of "churn_probability = 0.92". (3) A Streamlit dashboard with KPI cards, gauge charts, and color-coded risk levels (CRITICAL/HIGH/MODERATE/LOW) that anyone can understand at a glance.

**Result:** The dashboard became the primary tool for demonstrating the platform. Stakeholders could immediately see which customers to target, why they're at risk, and what actions to take — without understanding any ML.

### STAR Answer 4: "How do you ensure model quality in production?"

**Situation:** A model that works in a notebook can fail silently in production due to data drift, schema changes, or degrading performance.

**Task:** Build MLOps infrastructure to monitor, version, and maintain the churn model in production.

**Action:** I implemented: (1) Model versioning with a registry that tracks metrics, timestamps, and file paths for every trained model. (2) A ModelMonitor class that logs every prediction for audit and detects data drift by comparing feature distributions against baseline. (3) Automated retraining pipeline skeleton that triggers when drift exceeds a threshold. (4) Rotating log files with separate error logs. (5) Input validation that catches out-of-range values before prediction. (6) Docker containerization for consistent environments. (7) GitHub Actions CI/CD that runs the full pipeline on every push.

**Result:** The system is production-ready with full audit trails, drift detection, and automated testing. Any degradation would trigger alerts before it impacts business decisions.
